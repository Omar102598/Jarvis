# AGENTS.md — working on the Jarvis codebase

For any coding agent (Forge, Claude Code, others). Read this before changing
anything. `CLAUDE.md` imports this file.

## What runs where

| Where | What |
|---|---|
| **GCP VM `jarvis-core.tail7e74a7.ts.net`** (Docker, `docker-compose.core.yml`) | `llm_agent` (the brain, container `jarvis-llm`), `agent_runner` (all background agents), `mobile_gateway` (iOS/HTTP API, :8080), `dashboard` (:8888), `synapse`, `vision`, `redis` (:6379), `mosquitto` (MQTT :1883), `chroma`, `ring_mqtt` |
| **The Mac** (native processes) | `wake_word`, `stt`, `speaker_verify`, `tts_mac` (`scripts/run_audio_native.sh`), `mac_bridge` (:7777, `scripts/run_mac_bridge.sh`), Home Assistant (Docker, :8123) |
| **iPhone** | `JarvisApp/` (SwiftUI; project generated by xcodegen from `JarvisApp/project.yml`) |

Everything talks over Tailscale. Services talk to each other over MQTT and Redis.

## Repo map

- `services/llm_agent/` — the brain. `main.py` holds the tool list, prompt
  assembly and the stream loop; `tools/*.py` are LangChain `@tool`s;
  `plugins/` hot-reload.
- `services/agent_runner/` — scheduled/triggered agents (`*_agent.py`,
  scheduled by `config/agents.yml`).
- `services/mobile_gateway/` — FastAPI for the app (`/ask/*`, `/history`, pushes).
- `config/` — **volume-mounted at `/config` on the VM. Editable without a rebuild:**
  - `SOUL.md` — Jarvis's personality.
  - `prompts/brain/core.md` — the brain's operating rules.
  - `skills/<name>/SKILL.md` — playbooks the brain loads on demand.
  - `prompts/surfaces/*.md` — per-surface style.
  - `prompts/agents/<agent>/*.md` — background agents' prompts.
  - `agents.yml` (schedules), `mcp_servers.yml`.
- `scripts/golden_tasks.py` — regression gate. **Must pass before you call anything done.**

## Adding a brain tool (the whole checklist — all four steps, or it isn't done)

1. Write the `@tool` in `services/llm_agent/tools/<area>.py`. The docstring is
   what the model sees, so say when to use it.
2. Import it in `services/llm_agent/main.py` (the `from tools.<area> import …` block).
3. Add it to the tools list in `main.py` (the big list near the other tools of its area).
4. Make it findable. Tools are **deferred** (tool search), so the model only
   uses a tool it knows the name of. Name it in the matching
   `config/skills/<skill>/SKILL.md`, or create a new skill (front matter needs
   `name` and `description`, and the description says when to load it).

Then run `python3 -m py_compile` on the files you changed and `python3 scripts/golden_tasks.py`.

To show the user structured data in the app (a tracker, a table, a chart),
build a card with `tools/cards.py` (`cards.attach({...})`) and append the
returned marker to the tool's result. Card types are listed in that file's docstring.

## Changing an agent's behaviour

Edit its markdown in `config/prompts/agents/<agent>/`. Python loads it via
`prompt_files.agent_prompt("<agent>/<name>")`. Keep `{placeholders}` intact
when a module `.format()`s the prompt. A restart of `agent_runner` picks it up.

## Deploying

- **`config/` only:** commit, push, then on the VM run `cd ~/Jarvis && git pull`.
  The brain's prompt, skills and surfaces apply on the next turn. Agent prompts
  need `docker compose -f docker-compose.core.yml restart agent_runner`.
- **Service code (`services/<svc>/`):** commit and push to `develop`. The GitHub
  Actions "Build images" run builds `ghcr.io/…/jarvis-<svc>`. Then on the VM:
  `docker compose -f docker-compose.core.yml pull <svc> && docker compose -f docker-compose.core.yml up -d --no-build <svc>`.
  After a restart the brain takes about 75s (MCP loading) before it answers.
- **Native Mac services:** `scripts/run_audio_native.sh stop && … start`, or
  Forge's `rebuild_service`.
- **Never** `docker compose build/up` the core services on the Mac. That starts
  a second brain alongside the real one.
- Forge: don't commit or push unless the task says so. Report what needs deploying.
- **Forge's Ship flow** (Jarvis-repo tasks, `DEV_MODE=cloud`): `developer_agent`
  opens a `forge` issue, then `.github/workflows/forge.yml` runs Claude Code on a
  GitHub runner and opens a PR from `forge/issue-<n>`. Forge then files a "Ship"
  approval. Approving it squash-merges the PR (`forge_cloud.ship`), waits for
  "Build images", and writes `jarvis:deploy:request`. `scripts/vm_deploy.sh`
  (cron on the VM) then pulls and restarts what changed. It pauses while
  `~/Jarvis/.deploy-paused` exists. The log is `logs/deploy.log` on the VM.

## Verifying

- Test a brain change end to end by publishing a request with a fresh room id:
  `jarvis/llm/request` `{"text": "...", "room": "qa"}`. Then read the reply in
  Redis `conversation:default` and the tool calls in `jarvis:tool_events`
  (filter by `turn_id`). Delete test turns from `conversation:default` afterwards.
- Read-only questions only. Don't run test prompts that change real things
  (lights, thermostat, orders, bookings).

## Gotchas

- Claude 5.x models reject `temperature`. `llm_factory.py` never sends it to Claude.
- Redis on the VM is port **6379**. Native Mac services reach it over Tailscale.
- Never use paho `connect/publish/disconnect` without a loop. Use `paho.mqtt.publish.single`.
- MQTT payloads have a size limit. Images go through the gateway's stash, not inline.
- Times: the user is in `USER_TZ` (America/Chicago). Cron in recurring check-ins is local time.
- Don't touch `.env` or credentials.
- The Mac's `~/Documents` is TCC-protected. Processes started by launchd
  can't use it unless Full Disk Access is granted.
